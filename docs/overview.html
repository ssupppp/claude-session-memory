SHEET 01 / 05

The problem this solves for you

You run six to ten active codebases at once — a mix of work and personal projects, each with its own frontend, backend, or pipeline. Every one of them has its own history, its own open threads, its own half-finished decisions.

Without something carrying that forward, there are only two bad defaults. Either you re-explain the state of a project at the top of every session — real time, spent every day. Or everything lives in one global memory file that keeps growing and gets loaded in full no matter which project you're actually touching — real tokens, spent on context that has nothing to do with today's work.

The mental model: a filing clerk who only opens the drawer for the project you're standing in front of — never the whole cabinet, and never nothing at all.

That's the whole premise. Everything below is the mechanism that makes it true.

SHEET 02 / 05

Layout: one skill, many drawers

The skill itself is installed once. Every project it touches gets its own small set of files — nothing shared by default. A thin, optional index sits outside all of them, only written to if you explicitly ask for it.

SHEET 03 / 05

How it runs

Two modes, two very different postures. Starting a session only ever reads. Ending one is the only place anything gets written — and it writes selectively, not everything every time.

SHEET 04 / 05

The details

One SKILL.md, mode picked first, then either the START or END path below runs — never both.

FileCreated byPurpose
MEMORY.mdauto, first END runPer-project session history
ERRORS.mdonly when something genuinely failedRoot causes, so you don't re-debug the same thing
BACKLOG.mdnever auto-createdOnly touched if you already keep one
.claude/session-memory/.last-activeevery END runRecency signal — works even with no git history
~/.claude/session-memory/MEMORY.mdonly if you opt in, onceOne line per session, across every project

Config, per project

Optional .claude/session-memory.json overrides doc filenames and turns on the global log. Absent = sane defaults, zero setup.

Multi-project scan

If you've registered several projects, starting with no target sorts them by the .last-active marker — falls back to last git commit, works for non-git folders too.

The bug that got caught

git rev-parse --show-toplevel walks upward for a .git — a casual subfolder inside an unrelated parent repo could silently write into the wrong place. Fixed: both modes check the resolved root against your home directory before trusting it.

Selective, not exhaustive

ERRORS.md only gets an entry when something actually broke non-obviously — never a "nothing to report" line. That's what keeps it worth reading.

.claude/session-memory.json
{
  "globalMemory": "~/.claude/session-memory/MEMORY.md",
  "docs": { "memory": "MEMORY.md", "errors": "ERRORS.md", "backlog": "BACKLOG.md" }
}
SHEET 05 / 05

Is "session-memory" the right name?

Keep it — reposition, don't rename

The command reads naturally: you say "start session" or "session end" and it just does the thing you said. That match between what you'd naturally type and what the skill is called is worth more than a cleverer name — renaming it trades a small differentiation gain for a real cost in muscle memory and discoverability (people search "claude code session memory," not a coined term).

The honest risk isn't the name — it's the category. "Memory" skills are common now, and a generic name in a crowded shelf blends in. The fix for that is the description and pitch, not the command: lead publicly with what actually makes this one different — routing to the right doc instead of one dump, and working for non-git folders — rather than the word "memory" itself.

If you still want to weigh alternatives, here's how they trade off:

NameTrade-off
session-memoryMatches natural phrasing exactly. Generic category term — differentiation has to come from the pitch, not the name.
session-cascadeNames the actual mechanism (routed writes across docs). Less intuitive to type or search for.
continuityEvocative, short. Doesn't hint that it's session-scoped — reads more like a product name than a command.
docs-routerPrecise about what it does. Sounds infrastructural, undersells the briefing side entirely.
